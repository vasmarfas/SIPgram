# SIPgram

[![ci](https://github.com/vasmarfas/sipgram/actions/workflows/ci.yml/badge.svg)](https://github.com/vasmarfas/sipgram/actions/workflows/ci.yml)
[![license](https://img.shields.io/badge/license-PolyForm%20Noncommercial-blue)](LICENSE)

**[English version](README.md)**

Самостоятельно размещаемый шлюз между SIP и Telegram. SIPgram регистрируется на вашей FreePBX/Asterisk обычными
внутренними номерами и превращает звонки в **обычные звонки Telegram**: голосовые P2P-вызовы, не групповые чаты и
не голосовые сообщения. Один аккаунт-шлюз обслуживает всех пользователей одновременно.

* Входящий на внутренний 491, и шлюз звонит владельцу номера в Telegram, перед этим прислав в чат имя и номер звонящего.
* Отправили номер в чат, и шлюз перезванивает вам и соединяет с номером через АТС.
* Позвонили шлюзу сами, и он набирает номер по умолчанию (IVR, секретарь) или последний присланный.
* В разговоре: DTMF, второй вызов с удержанием первого (АТС играет музыку), переключение, перевод,
  автопереподключение при обрыве Telegram.
* Маршрутизация, запись, очереди, follow-me и CDR остаются на стороне АТС: для неё это просто SIP-телефоны.
* Запись разговора приходит голосовым сообщением в чат и нигде не хранится.
* Opus 48 кГц на SIP-плече, поэтому широкополосный звук доходит от Telegram до внутреннего номера без сужения.
* Конференция на АТС, HTTP API для CRM, уведомления администратору о проблемах, несколько аккаунтов-шлюзов.
* Расписание входящих: рабочие и тихие часы, чёрный и белый списки номеров, переадресация отфильтрованных на АТС.
* Групповой звонок Telegram: собеседник добавляет людей прямо в звонке, либо `/group` переносит разговор в голосовой
  чат группы или в конференцию Telegram без группы. Абонент АТС остаётся в разговоре.
* Опциональный бот с кнопками: клавиатура DTMF, удержание и переключение, перевод, обратный звонок. Звонок занимает в
  чате одно сообщение-карточку: входящий, разговор, итог.
* Отвечать можно в любом клиенте Telegram, включая Telegram Web.
* Linux в Docker или нативно, и Windows, без компиляции: достаточно `pip install`.

```
 PSTN / SIP-транк ──► FreePBX ──SIP/RTP (Opus, G.711)──► SIPgram ──Telegram P2P (MTProto)──► Telegram пользователей
                      Asterisk                          Python: свой SIP-стек + NTgCalls + Telethon
```

## Что нужно

1. **Отдельный Telegram-аккаунт для шлюза** на любом номере, куда приходит SMS. Telegram не звонит самому себе,
   поэтому шлюзу нужен свой аккаунт. Одного хватает на всех: он держит до `telegram.max_calls` разговоров параллельно.
2. `api_id` и `api_hash` с <https://my.telegram.org> (API development tools).
3. Внутренний номер с паролем на АТС, по одному на пользователя.
4. Telegram id пользователей (написать `@userinfobot`) или их @username.
5. По желанию токен бота от `@BotFather` для кнопок.
6. Linux с glibc 2.28 и новее (Debian 10+, Ubuntu 20.04+, не Alpine) либо Windows 10/11 x64, Python 3.10–3.14.
   Либо Docker, он закрывает вариант с Linux.

## Быстрый старт в Docker

```bash
git clone https://github.com/vasmarfas/sipgram.git && cd sipgram
mkdir -p config sessions
sudo chown -R 1000:1000 config sessions
cp config.example.yaml config/config.yaml
cp .env.example .env
docker compose build
docker compose run --rm sipgram login
docker compose run --rm sipgram whoami
docker compose run --rm sipgram check
docker compose up -d && docker compose logs -f
```

До шага `login` заполните в `config/config.yaml` поля `api_id`, `api_hash`, `users`, `sip.server` и `sip.accounts`,
а в `.env` пароли внутренних номеров. `login` спрашивает телефон аккаунта-шлюза, код из SMS и пароль 2FA, делается
один раз. `whoami` показывает сессию, разрешённых пользователей и бота, `check` регистрирует каждый номер.

Процесс в контейнере работает под uid 1000, поэтому оба примонтированных каталога должны принадлежать ему,
отсюда `chown`. Без него первый `login` падает с `Permission denied` при записи файла сессии.

Готовый образ собирается при каждом пуше в основную ветку, для `linux/amd64` и `linux/arm64`:

```bash
docker pull ghcr.io/vasmarfas/sipgram:latest
```

Чтобы взять его вместо локальной сборки, замените в `docker-compose.yml` строку `build: .` на
`image: ghcr.io/vasmarfas/sipgram:latest`.

Контейнер работает в `network_mode: host`, поэтому SIP-порты номеров (5070, 5071 и далее) и диапазон RTP
(`rtp_port_min`–`rtp_port_max`, по умолчанию 40000–40200/udp) должны быть доступны АТС. `docker compose ps`
показывает health, он берётся из `sipgram status`.

## Быстрый старт без Docker

```bash
python -m venv venv
. venv/bin/activate
pip install -e .
cp config.example.yaml config.yaml
export SIP_PASSWORD_491=...
sipgram login
sipgram whoami
sipgram check
sipgram run
```

На Windows окружение активируется через `venv\Scripts\activate`, пароль задаётся как
`$env:SIP_PASSWORD_491 = "..."`, остальные особенности платформы в разделе [Windows](#windows).

Если конфиг не в текущем каталоге, используйте `sipgram -c путь/к/config.yaml <команда>`, для подробного лога
`sipgram -v --sip-trace run`.

| Команда | Что делает |
|---|---|
| `sipgram run` | Запускает шлюз. |
| `sipgram login [шлюз]` | Интерактивный вход в Telegram, один раз на каждый аккаунт-шлюз. |
| `sipgram whoami` | Показывает сессии, разрешает пользователей из конфига, проверяет бота. |
| `sipgram check [номер]` | Один раз регистрирует каждый номер и печатает результат. |
| `sipgram doctor [--offline]` | Проверяет конфиг, каталоги, порты, DNS, регистрацию, сессии, libopus, расписание. |
| `sipgram status` | Здоровье запущенного шлюза по файлу состояния. Код возврата 0 значит всё в порядке. |

## Сторона Telegram

* Каждый пользователь добавляет аккаунт-шлюз в контакты либо разрешает звонки всем (Настройки, Конфиденциальность,
  Звонки). Иначе Telegram отклонит вызов с `USER_PRIVACY_RESTRICTED`: АТС получит 480, а пользователю в чат придёт
  объяснение, что поправить.
* Шлюз сам добавляет пользователей в свои контакты, чтобы принимать их вызовы.
* Аккаунту-шлюзу стоит дать понятное имя и аватар, например «Офис»: звонки в Telegram будут приходить от него.
* Если задан `bot_token`, каждый пользователь один раз нажимает в боте Start. Дальше уведомления и кнопки приходят
  от бота, а сами звонки от аккаунта-шлюза. Без бота всё работает текстовыми командами.
* Не используйте для шлюза только что зарегистрированный аккаунт: Telegram ограничивает свежие аккаунты.

## Сторона АТС

Для АТС шлюз это набор обычных SIP-телефонов: каждый номер из `sip.accounts` регистрируется отдельно. Ниже
FreePBX 15/16/17 (Asterisk 16–22, chan_pjsip), в конце раздела есть `pjsip.conf` для голого Asterisk.

### Внутренний номер на каждого пользователя

Applications, Extensions, Add Extension, **Add New SIP [chan_pjsip] Extension**.

| Поле | Значение |
|---|---|
| User Extension | номер, например `491` |
| Display Name | имя владельца, его увидят на АТС при звонках из Telegram |
| Secret | длинный пароль, он же в `password` аккаунта или в `.env` как `SIP_PASSWORD_491` |

Вкладка **Advanced**:

| Поле | Значение | Зачем |
|---|---|---|
| Max Contacts | 1 | одна регистрация с номера |
| Codecs (Allowed) | `opus`, `ulaw`, `alaw`, при желании `slin16` | порядок задаёт приоритет |
| DTMF Signaling | RFC 4733 | соответствует значению по умолчанию `dtmf: rfc2833` |
| Direct Media | No | RTP всегда через Asterisk |
| Rewrite Contact | Yes | Asterisk отвечает на реальный адрес и порт шлюза за NAT |
| RTP Symmetric | Yes | RTP уходит туда, откуда пришёл |
| Force rport | Yes | |
| Qualify Frequency | 60 | OPTIONS-пинги, SIPgram на них отвечает |
| Allow Transfer | Yes | нужно для `/transfer <номер>` (REFER) |
| Call Waiting | Yes | второй вызов доходит до шлюза, при No АТС сама отвечает «занято» |
| Music on Hold Class | любой | это услышит собеседник на удержании |

Voicemail, Follow Me и ring time настраиваются по вкусу. Они срабатывают, когда Telegram не ответил за
`ring_timeout`: АТС получает 480 и идёт по своей цепочке. Submit, затем Apply Config.

В `config.yaml`:

```yaml
sip:
  server: pbx.example.com
  accounts:
    - {username: "491", password: "${SIP_PASSWORD_491}", user: 123456789}
    - {username: "492", password: "${SIP_PASSWORD_492}", user: "@petya"}
```

### Сеть

* Шлюз рядом с АТС, та же сеть или тот же хост: дополнительных настроек нет. На хосте с FreePBX порт 5060 занят
  Asterisk, поэтому у номеров свои порты, начиная с `local_port: 5070`.
* Шлюз за NAT, АТС в интернете: обычно достаточно Rewrite Contact и RTP Symmetric на номере. Явно объявить адрес
  можно через `sip.public_ip`. Пробросьте `local_port`/udp и диапазон `rtp_port_min`–`rtp_port_max` либо положитесь
  на симметричный RTP, так как шлюз шлёт RTP первым.
* АТС за NAT: Settings, Asterisk SIP Settings, NAT Settings, External Address и Local Networks. Без этого в SDP от
  АТС окажется приватный адрес и звука не будет.
* Файрвол FreePBX и fail2ban: внесите адрес шлюза в Connectivity, Firewall, Networks как Local или Trusted, иначе
  после нескольких перерегистраций он может попасть в бан.
* Транспорт: UDP по умолчанию. Для TCP или TLS включите транспорт в Asterisk SIP Settings и задайте
  `transport: tcp|tls`, для TLS ещё `port: 5061`. Для самоподписанного сертификата `tls_verify: false`.
* Legacy chan_sip слушает другой порт (в FreePBX обычно 5160). Номера из `sip.accounts` должны быть заведены в том
  драйвере, чей порт указан в `sip.port`.

### Входящие звонки

Направьте вызовы на номер пользователя штатно:

* Connectivity, Inbound Routes, Set Destination, Extensions, 491;
* Ring Group или Queue из таких номеров: Telegram позвонит каждому владельцу, первый ответивший получает разговор,
  остальным АТС отбивает вызов;
* Follow Me на основном номере с добавлением 491.

Пока Telegram звонит, у АТС 180 Ringing и она играет звонящему свой ringback. Отклонение в Telegram превращается в
603, занято в 486, отсутствие ответа в 480. FreePBX обрабатывает всё это штатно.

Один номер на несколько людей (семья, дежурная смена): `users: [id1, id2]` вместе с `ring_all: true` звонит всем
одновременно, первый ответивший забирает вызов. Без `ring_all` звонит только первый в списке.

### Исходящие звонки

Шлюз отправляет INVITE на `sip:<номер>@<domain>` от имени номера пользователя, поэтому Outbound Routes и права
номера (контекст `from-internal`) работают как обычно. CallerID наружу такой, как настроен для номера.

Присланный номер проходит через `calls.dial_rules`: по умолчанию удаляются пробелы, скобки и дефисы, ведущий `+`, а
`8XXXXXXXXXX` превращается в `7XXXXXXXXXX`. Подстройте правила под свои Outbound Routes.

В INVITE добавляются заголовки `X-TG-User-Id` и `X-TG-User-Name`, они пригодятся в диалплане
(`${PJSIP_HEADER(read,X-TG-User-Id)}`) для CDR или маршрутизации.

### Удержание, второй вызов, перевод

Всё делается стандартными средствами SIP, кроме уже упомянутых Allow Transfer и Call Waiting включать нечего:

* удержание это re-INVITE с `a=sendonly`, Asterisk включает собеседнику музыку из класса MOH номера;
* второй входящий звонит на тот же номер, шлюз отвечает 180 и ждёт решения пользователя `ring_timeout` секунд;
* `/transfer <номер>` отправляет REFER, Asterisk сам соединяет собеседника с номером и завершает плечо шлюза;
* `/transfer` при двух вызовах соединяет их внутри шлюза, оба остаются его каналами и CDR продолжается.

### Режим шлюза: звонки из АТС произвольным пользователям Telegram

Заведите общий номер:

```yaml
sip:
  accounts:
    - {username: "tg-trunk", password: "${SIP_PASSWORD_TRUNK}", shared: true}
```

Входящий на него маршрутизируется по набранному номеру (user part Request-URI):

| Набрано | Кому |
|---|---|
| `+79991234567` | пользователю Telegram с этим номером, шлюз импортирует его как контакт; номер должен быть виден |
| `tg#username` | этому @username |
| `123456789` (6 цифр и больше) | этому числовому Telegram id |

Адресат должен быть в списке `users`. Чтобы АТС передавала такой номер, нужен транк, а не extension: Connectivity,
Trunks, Add Trunk, chan_pjsip.

* Trunk Name `sipgram`; pjsip Settings, General: Authentication None, Registration None, SIP Server это адрес шлюза,
  SIP Server Port это `local_port` общего номера, Context `from-internal`.
* Advanced: From User `tg-trunk`, кодеки ulaw и alaw.
* Outbound Route с dial pattern `tg#.` или `+X.` на транк `sipgram`.

Пользователи без собственного номера звонят наружу через общий. Новые вызовы и SIP MESSAGE шлюз принимает только с
адреса `sip.server` и из сетей `sip.allow_from`, остальное отбрасывает с предупреждением в логе. Аутентификации
входящих при этом нет, поэтому не выставляйте его SIP-порты в интернет без файрвола.

### Голый Asterisk без FreePBX

```ini
; pjsip.conf
[491]
type=endpoint
context=from-internal
disallow=all
allow=opus,alaw,ulaw
auth=491
aors=491
direct_media=no
rtp_symmetric=yes
force_rport=yes
rewrite_contact=yes
dtmf_mode=rfc4733
allow_transfer=yes
moh_suggest=default
callerid="John" <491>

[491]
type=auth
auth_type=userpass
username=491
password=ОЧЕНЬ_ДЛИННЫЙ_ПАРОЛЬ

[491]
type=aor
max_contacts=1
qualify_frequency=60
```

```ini
; extensions.conf
[from-internal]
exten => 491,1,Dial(PJSIP/491,40)
 same => n,Hangup()
```

Ровно такой конфиг используется в интеграционных тестах, см. `tests/integration/asterisk/`.

## Конфигурация

Полный пример с комментариями лежит в [config.example.yaml](config.example.yaml). Минимум:

```yaml
telegram:
  api_id: 12345
  api_hash: "0123456789abcdef0123456789abcdef"
  session: gateway
users:
  - {id: 123456789, name: Иван}
sip:
  server: pbx.example.com
  accounts:
    - {username: "491", password: "${SIP_PASSWORD_491}", user: 123456789}
```

| Параметр | Значение |
|---|---|
| `telegram.max_calls` | сколько разговоров одновременно держит аккаунт-шлюз, по умолчанию 10 |
| `telegram.bot_token` | токен бота для кнопок, пусто значит только текстовые команды |
| `telegram.gateways` | дополнительные аккаунты-шлюзы, `users[].gateway` привязывает пользователя к одному из них |
| `telegram.language`, `users[].language` | стартовый язык интерфейса (`ru` или `en`), каждый переключает себе сам командой `/lang`, выбор запоминается |
| `users[]` | id, @username или +телефон, а также `name` и `can_call: false` для тех, кто только принимает |
| `sip.*` | значения по умолчанию для всех номеров: server, port, transport (`udp`/`tcp`/`tls`), codecs, RTP-порты, `public_ip`, `allow_from` (адреса и сети, с которых кроме `sip.server` принимаются вызовы) |
| `sip.accounts[].user` / `users` | владельцы номера, первый принимает входящие, `ring_all: true` звонит всем сразу и вызов забирает первый ответивший |
| `sip.accounts[].shared` | общий номер-транк: АТС набирает через него `tg#username`, `+7999…` или id, а пользователи без своего номера звонят через него наружу |
| `sip.accounts[].ring_timeout` | сколько секунд звонить в Telegram, потом АТС получает 480 и идёт по своей логике |
| `sip.accounts[].default_destination` | куда соединять, если владелец позвонил шлюзу, не прислав номер |
| `calls.outgoing_mode` | `callback` (сначала звонок вам, потом набор) или `direct` (набор сразу) |
| `calls.call_waiting` | второй входящий во время разговора: звонит и предлагает `/switch`, при `false` сразу «занято» |
| `calls.reconnect_timeout` | при обрыве Telegram собеседник уходит на удержание, а шлюз перезванивает вам столько секунд |
| `calls.dial_rules` | регулярки-преобразования присланного номера |
| `calls.ringback` | гудки, пока АТС дозванивается: `ru`, `us`, `none` |
| `calls.record` | `off`, `ask` (включается командой `/rec`) или `all`, запись уходит голосовым сообщением и не сохраняется |
| `calls.conference_extension` | номер комнаты ConfBridge на АТС, включает `/conf` |
| `calls.group_chat` | группа Telegram, в голосовом чате которой собирается `/group`; пусто значит конференцию Telegram без группы |
| `schedule.*` | рабочие и тихие часы, чёрный и белый списки, что делать с отфильтрованным вызовом; по умолчанию пусто и фильтрации нет |
| `users[].schedule` | то же для одного пользователя, недостающие ключи берутся из общего раздела |
| `notifications.admin` | кому слать уведомления о потере регистрации, проблемах Telegram, старте и остановке |
| `api.*` | HTTP API для CRM и скриптов, см. [HTTP API](#http-api) |

Любое значение вида `${VAR}` берётся из окружения, так что секреты можно не писать в YAML (для Docker это `.env`).
Старый формат конфига v0.1 (`lines:`) читается и мигрирует на лету, в лог пишется подсказка.

## Использование

Всё управление идёт в чате с аккаунтом-шлюзом или в боте, где те же действия доступны кнопками.

| Действие | Как |
|---|---|
| Входящий с АТС | Сообщение с именем и номером звонящего, следом звонок Telegram. Не ответили за `ring_timeout`, АТС получает 480 и идёт на voicemail или follow-me; сбросили, приходит 603 Decline. С ботом всё это одна карточка: входящий, разговор, итог звонка с кнопкой «Перезвонить». |
| Позвонить наружу | Отправьте номер (`+7 999 123-45-67`, `8903…`, `101`, `sip:user@host`). Шлюз перезвонит и наберёт. Пока АТС дозванивается, слышны гудки или ранние медиа АТС. Если номеров несколько, `/line` показывает и выбирает линию, а `491: 101` набирает через конкретную. |
| Позвонить шлюзу | Соединяет с `default_destination` вашей линии либо с последним присланным номером в пределах `pending_number_ttl`. Так же работает приглашение шлюза в групповой звонок Telegram: он подключается и заводит туда номер. |
| DTMF | В разговоре отправьте цифры, `*`, `#` (`1`, `123#`) или `/dtmf 123`, в боте есть клавиатура. Вы услышите тон нажатия в трубке, а шлюз повторит цифры сообщением. По умолчанию цифры идут вне полосы (RFC 4733), поэтому собеседник-человек их не слышит; если нужно, чтобы слышал, поставьте `dtmf: inband`. Коды вида `*1…` перехватывает сама АТС, см. [Диагностику](#диагностика). |
| Сервисные коды | Вне разговора отправьте код (`*97`, `*43`), шлюз наберёт его как обычный номер, перехвата in-call кодов при этом нет. |
| Второй входящий | Приходит сообщение «Второй входящий»: `/switch` принимает его и ставит текущий на удержание с музыкой от АТС, `/decline` отклоняет. Дальше `/switch` переключает между двумя разговорами, `/hangup` завершает текущий и возвращает удержанный. |
| Второй исходящий | `/call 102` в разговоре ставит текущий на удержание и набирает 102. Дальше `/switch` или `/transfer`. |
| Перевод | `/transfer` при двух вызовах соединяет их между собой и выводит вас (attended). `/transfer 102` переводит собеседника на 102 через REFER (blind). |
| Завершить | Положить трубку в Telegram (завершает всё) или `/hangup` (только текущий вызов). |
| Обрыв связи | Если Telegram-звонок оборвался не по вашей воле, собеседник ставится на удержание, а шлюз перезванивает вам до `reconnect_timeout` секунд. |
| Добавить людей | В звонке Telegram нажмите «Добавить участника». Звонок станет групповым, шлюз перейдёт в него вместе с абонентом АТС, в карточке появится число участников. Когда в звонке не остаётся никого, кроме шлюза, линия АТС завершается. |
| Ключ шифрования | В карточке звонка четыре эмодзи. Если они совпадают с эмодзи на экране звонка в Telegram, ключ между вами и шлюзом общий и посередине никого нет. |
| `/cb`, `/redial` | Перезвонить последнему звонившему, повторить последний набор. |
| `/dnd` | Не беспокоить: входящие с АТС получают «занято». |
| Расписание | `/schedule` показывает ваши рабочие и тихие часы, списки номеров и принимаете ли вы звонки прямо сейчас. Настраивается в разделе `schedule`, по умолчанию пусто. |
| `/status`, `/history`, `/help` | Состояние линий и разговоров, последние 10 звонков, подсказка по командам. |
| Язык | `/lang en` или `/lang ru` переключает интерфейс только для вас и запоминается между перезапусками. |
| Запись | `/rec` включает и выключает запись текущего разговора. Когда запись останавливается или звонок завершается, она приходит голосовым сообщением. На диск ничего не пишется. При `calls.record: all` пишется каждый разговор. |
| Конференция | `/conf` переводит текущий и удерживаемый вызовы в комнату ConfBridge на АТС и подключает туда вас. `/conf 101` дополнительно звонит на 101 и заводит его в ту же комнату. |
| Групповой звонок | `/group` переносит разговор в групповой звонок Telegram: в голосовой чат группы `calls.group_chat` либо, если группа не задана, в новую конференцию Telegram. Линии АТС остаются на шлюзе, а Telegram-звонок заменяется приглашением. `/group @petya` дополнительно зовёт человека, `/group 101` заводит внутренний номер, `/group stop` завершает всё, `/hangup` только ваши линии. |

Функциональные коды FreePBX (`##` перевод, `*2` парковка) тоже работают через DTMF, если включены для номера.

## Несколько пользователей

Каждому заводится свой extension в `sip.accounts` с `user:`. Разговоры разных пользователей идут параллельно через
один аккаунт-шлюз, при этом у каждого пользователя один разговор плюс удержание и ожидание второго. Один extension
на нескольких людей задаётся через `users: [...]` с `ring_all: true`: звонит всем, первый ответивший забирает
вызов, остальные видят пропущенный. Для звонков из АТС произвольным людям в Telegram используется общий номер, см.
[Режим шлюза](#режим-шлюза-звонки-из-атс-произвольным-пользователям-telegram).

## HTTP API

Выключен по умолчанию. Включается в `config.yaml`:

```yaml
api:
  enabled: true
  bind: 127.0.0.1
  port: 8080
  token: "${SIPGRAM_API_TOKEN}"
  allow: ["10.0.0.0/8"]
  rate_limit: 120
```

В Docker при `network_mode: host` порт открывается на самом хосте, поэтому оставляйте `bind: 127.0.0.1`, если
наружу его пускать не нужно.

Каждый запрос, кроме `/api/health`, требует токен в заголовке `Authorization: Bearer <токен>` или `X-Api-Token`.
Токен сравнивается за постоянное время. Неверный даёт 401, адрес вне `allow` даёт 403, превышение `rate_limit`
даёт 429. Все отказы пишутся в лог с адресом клиента.

| Метод и путь | Что делает |
|---|---|
| `GET /api/health` | Без токена. `{"ok": true, "accounts": {...}}` либо 503, если хотя бы один номер не зарегистрирован. Подходит для мониторинга. |
| `GET /api/status` | Аккаунты-шлюзы с загрузкой, SIP-номера с состоянием регистрации, все активные разговоры. |
| `GET /api/users` | Пользователи: id, язык, режим «не беспокоить», их линии и аккаунт-шлюз. |
| `GET /api/history?user=<id>&limit=20` | История звонков пользователя. |
| `POST /api/calls` | Click-to-call. Тело: `{"user": 123, "number": "+7 999 …", "account": "491"}`, поле `account` необязательно. |
| `POST /api/calls/<user>/hangup` | Завершить текущий разговор пользователя. |
| `POST /api/calls/<user>/dtmf` | `{"digits": "123#"}` в активный разговор. |
| `POST /api/calls/<user>/transfer` | `{"number": "101"}`, перевод через REFER. |
| `POST /api/messages` | `{"user": 123, "text": "…"}`, сообщение пользователю от шлюза. |

`user` это числовой id либо то же значение, что в `users[].id` конфига.

```bash
curl -X POST http://127.0.0.1:8080/api/calls \
  -H "Authorization: Bearer $SIPGRAM_API_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"user": 123456789, "number": "+7 999 123-45-67"}'
```

Дальше всё как при отправке номера в чат: шлюз перезвонит менеджеру в Telegram и соединит.

Коды ответов: 200 выполнено, 400 неверное тело запроса, 401 токен, 403 адрес, 404 нет такого пользователя,
409 действие невозможно в текущем состоянии (нет активного звонка, линия занята), 429 лимит запросов,
500 внутренняя ошибка, она пишется в лог с трассировкой.

## Windows

SIPgram работает как обычное консольное приложение: Python 3.10–3.14 x64, `pip install`, без компиляторов, потому
что колесо `ntgcalls` для Windows x64 есть на PyPI. Проверено на Windows 11 с Python 3.14.

```powershell
winget install Python.Python.3.12
cd C:\sipgram
python -m venv venv
venv\Scripts\activate
pip install -e .
copy config.example.yaml config.yaml
$env:SIP_PASSWORD_491 = "секрет"
sipgram login
sipgram check
sipgram run
```

При первом запуске брандмауэр Windows спросит разрешение для `python.exe`, разрешите для частных сетей. Если АТС в
другой сети, откройте на хосте `local_port`/udp и диапазон `rtp_port_min`–`rtp_port_max`/udp.

Автозапуск делается либо через Планировщик заданий (триггер «При запуске», действие
`C:\sipgram\venv\Scripts\sipgram.exe -c C:\sipgram\config.yaml run`, галка «Выполнять вне зависимости от входа
пользователя», пароли в системных переменных окружения), либо через [NSSM](https://nssm.cc):
`nssm install sipgram C:\sipgram\venv\Scripts\sipgram.exe -c C:\sipgram\config.yaml run`, файл для stdout на
вкладке I/O или `logging.file` в конфиге.

Особенности платформы:

* При старте вызывается `timeBeginPeriod(1)`, иначе шаг системного таймера 15,6 мс ломает 20-мс пакетизацию RTP.
* Завершение процесса идёт через `TerminateProcess`, потому что ntgcalls на Windows блокирует нормальный выход
  интерпретатора. Сессии Telegram и регистрация SIP при этом закрываются корректно: де-регистрация отправляется до
  выхода.
* Docker Desktop для запуска самого шлюза на Windows не рекомендуется: `network_mode: host` там недоступен, а RTP
  через его NAT работает ненадёжно. Нативный запуск проще.

## Диагностика

`sipgram doctor` проверяет всё сразу: конфиг, права на каталоги, порты SIP и RTP, DNS, регистрацию на АТС, сессии
Telegram, бота, libopus и расписание. Код возврата 0 значит, что ничего не сломано. Сетевые проверки пропускает
`--offline`, в Docker команда выглядит как `docker compose run --rm sipgram doctor`.

Подробный лог включается флагами `sipgram -v --sip-trace <команда>` либо ключами `logging.level: DEBUG` и
`logging.sip_trace: true` в конфиге. В Docker: `docker compose logs -f`.

**`registration failed: 401 Unauthorized` или `403 Forbidden`.** Неверный `username`, `password` или
`auth_username`, номер заведён не в chan_pjsip, либо адрес шлюза забанен файрволом FreePBX (Connectivity, Firewall,
Intrusion Detection).

**`registration failed: 408 no response`.** До АТС не доходит UDP: неверный `server`, `port` или транспорт, либо
файрвол. Запустите `sipgram -v --sip-trace check`: строка `UDP send/receive error` рядом с исходящим REGISTER
значит, что пакет не ушёл с самого хоста.

**Входящие не приходят, хотя регистрация есть.** АТС шлёт INVITE на Contact шлюза, посмотрите
`asterisk -rx "pjsip show contacts"`. Приватный адрес там значит, что нужен Rewrite Contact или `sip.public_ip`.

**Нет звука или звук в одну сторону.**

* От Telegram к телефону нет: АТС не получает наш RTP, значит в SDP от АТС приватный адрес (NAT Settings) либо
  мешает файрвол.
* От телефона к Telegram нет: наш диапазон RTP недоступен для АТС либо не задан `sip.public_ip` за NAT.
  RTP Symmetric на номере обычно решает вопрос, так как шлюз шлёт RTP первым.
* `488 Not Acceptable Here` в логе значит, что нет общего кодека: включите opus или ulaw/alaw на номере.

**Звонок обрывается через 30 секунд.** Не доходит ACK, в логе `no ACK for final response`. Обычно это NAT и адрес в
Contact или Via.

**`USER_PRIVACY_RESTRICTED`, для АТС 480.** У вызываемого закрыты звонки, шлюз пишет ему об этом в чат. Пусть
добавит аккаунт-шлюз в контакты или в исключения для звонков.

**`INVITE from … ignored` в логе.** АТС шлёт вызовы не с того адреса, в который резолвится `sip.server` (несколько
интерфейсов, кластер). Добавьте этот адрес или сеть в `sip.allow_from`.

**`cannot resolve user 123456789`.** Шлюз ещё не видел этого пользователя. Напишите шлюзу с этого аккаунта любое
сообщение или укажите пользователя как `@username` либо `+телефон`.

**`FLOOD_WAIT_X` или `PEER_FLOOD`.** Telegram просит подождать или счёл активность спамом. Используйте аккаунт с
историей, звоните только контактам, не запускайте автообзвон.

**Звонок принят, но media уходит в CONNECTING и потом FAILED.** WebRTC/UDP не доходит до relay-серверов Telegram.
Проверьте исходящий UDP с хоста и блокировки Telegram-звонков в вашей сети.

**Звонок соединился, но тишина.** В логе есть `bridge stopped: sip->tg N frames, tg->sip M frames`. `tg->sip 0`
значит, что NTgCalls не отдаёт кадры, `sip->tg 0` значит, что нет RTP от АТС.

**Задержка или треск.** Увеличьте `calls.jitter_ms` до 60–100 при плохой сети между шлюзом и АТС, уменьшите до 20
при локальной АТС.

**В ответ на `*1…` слышно «Access denied».** Это FreePBX, а не шлюз: `*1` в разговоре зарезервирован под One Touch
Record. Asterisk перехватывает эти две цифры и, если запись по требованию для номера не разрешена, проигрывает
«Access denied», а остаток набора уходит дальше. Лечится в Applications, Extensions, Recording, On Demand
Recording или в Admin, Feature Codes.

**Цифры не слышно ни собеседнику, ни вам, но они доходят.** Так и должно быть при `dtmf: rfc2833`, ровно как на
обычном SIP-телефоне: цифра едет отдельным RTP-событием мимо звука, IVR её видит, а человек на другом конце нет.
Если тон должен быть слышен, поставьте номеру `dtmf: inband`.

**Кнопок нет, всё приходит от аккаунта-шлюза.** Бот пишет только тем, кто нажал в нём Start, его @имя показывает
`sipgram whoami`.

**Запись не включается, в логе `recording is not available`.** Нет libopus. В Docker он ставится из Dockerfile,
при нативном запуске это `apt install libopus0`.

**Звонки не приходят, хотя всё зарегистрировано.** Посмотрите `/schedule` в чате или `sipgram doctor`: скорее всего
действуют `schedule.work_hours` или `quiet_hours`. Время берётся локальное для процесса, поэтому в
`docker-compose.yml` нужно задать `TZ`, иначе внутри контейнера UTC.

**`GROUPCALL_FORBIDDEN` при старте голосового чата.** У аккаунта-шлюза нет права управлять видеочатами: выдайте
ему соответствующую админку либо начните голосовой чат вручную, шлюз подключится к идущему.

**Пользователь получает «занято» (486), хотя свободен.** Либо достигнут `telegram.max_calls` (в логе
`gateway at capacity`), либо пользователь в `/dnd`.

**`WinError 10048` на Windows.** Другой экземпляр или софтфон занял `local_port` или RTP-порты.

125 модульных тестов, около 15 секунд: SIP-парсер, digest по вектору RFC 2617, SDP offer и answer, G.711 и Opus,

регистрация по UDP и TCP, неверный пароль, исходящий на `Echo()` со спектральной проверкой вернувшегося тона,

входящие через AMI Originate, удержание и возобновление, перевод REFER и два одновременных диалога на одной
регистрации. Оба набора гоняются в CI на каждый пуш.

## Как устроено

```
sipgram/
  __main__.py      CLI: run / login / whoami / check / status / doctor
  config.py        YAML в dataclasses, ${ENV}, миграция формата v0.1
  gateway.py       запуск: аккаунт-шлюз, NTgCalls, бот, менеджер, файл состояния для healthcheck
  manager.py       CallManager: пользователи, SIP-аккаунты, параллельные звонки, удержание, перевод, команды, карточка
  bridge.py        CallBridge (Telegram и SIP: тикер 20 мс, джиттер-буфер, гудки), SipSipBridge, GroupBridge
  messages.py      тексты RU и EN, форматирование номеров и длительности
  prefs.py         настройки пользователя между перезапусками
  alerts.py        уведомления администратору с подавлением дребезга
  api.py           HTTP API на aiohttp
  history.py       журнал звонков на пользователя с ротацией
  schedule.py      окна расписания, шаблоны номеров, решение по входящему
  doctor.py        команда doctor
  sip/             свой SIP-стек: парсер сообщений, digest, SDP, кодеки, обёртка libopus, RTP, RTCP, транспорты, аккаунт
  tg/              аккаунт Telethon, движок NTgCalls, групповые звонки и конференции, опциональный бот, уведомления
  audio/           PCM-буфер, ресемплер, контейнер Ogg/Opus, запись в память, генератор тонов
```

На пользователя приходится не больше одного звонка Telegram (`UserState.tg`). К нему крепятся SIP-плечи: `active`
(мостится с Telegram), `held` (АТС играет MOH) и `waiting` (второй входящий, ещё звонит). Переходы сериализуются
`UserState.lock`. Разные пользователи полностью независимы: NTgCalls держит звонки по id собеседника, SipAccount
держит диалоги по Call-ID, поэтому параллельные разговоры не требуют дополнительной синхронизации.

SIP-стек это компактный поднабор RFC 3261 на asyncio, ровно столько, сколько нужно телефону за АТС: REGISTER с
digest (MD5 и SHA-256, qop), INVITE/ACK/BYE/CANCEL в обе стороны, ретрансмиссии T1/T2 для UDP, ответы на
OPTIONS/INFO/NOTIFY/UPDATE/MESSAGE, re-INVITE для удержания и session timers, REFER с NOTIFY sipfrag, транспорты
UDP, TCP и TLS. Компиляции он не требует и одинаково работает на Linux и Windows.

Сторона Telegram управляет NTgCalls напрямую, MTProto идёт через Telethon, без прослойки pytgcalls.
Последовательность вызовов та же, плюс `phone.receivedCall`, точные таймауты дозвона и явные причины
`discardCall`, чтобы АТС получала осмысленные коды (486, 480, 603) и корректно уходила на voicemail или follow-me.

Когда собеседник добавляет людей, Telegram сбрасывает частный звонок с причиной
`phoneCallDiscardReasonMigrateConferenceCall`. Шлюз заходит в конференцию по slug из этой причины, забирая медиа
частного звонка, и дальше сам ведёт её E2E-цепочку: применяет блоки, отвечает на запросы подцепочек, сообщает
NTgCalls, какой SSRC чей. Приглашение `messageActionConferenceCall` от пользователя обрабатывается как входящий звонок.

NTgCalls 3 выполняет вызовы в пуле потоков, и два кадра по 10 мс, отданные подряд, могли обогнать друг друга: на
Windows так случалось с 3–4% кадров. Поэтому кадры уходят через `FrameSender` строго по одному.

Ресемплинг в обычном случае не нужен: частота внешних кадров NTgCalls выставляется равной частоте SIP-кодека, а
WebRTC внутри NTgCalls сам ресемплирует в Opus 48 кГц. Направление Telegram в SIP пакетируется тикером 20 мс с
буфером `jitter_ms`, направление SIP в Telegram отдаётся кадрами по 10 мс сразу по приходу RTP, а джиттер
компенсирует NetEq на стороне клиента.

Запись разговора кодируется в Opus на лету (20 кбит/с, около 2,5 КБ/с) и лежит в контейнере Ogg в памяти, поэтому
десятиминутный разговор занимает около полутора мегабайт. Когда мост останавливается, файл уходит в чат и забывается.

## Ограничения

* Один разговор на пользователя плюс удержанный и ожидающий. Параллельность работает между пользователями.
* Сколько одновременных вызовов реально выдержит один аккаунт Telegram, решает Telegram. На первых прогонах держите
  `max_calls` небольшим.
* Только голос. SIP-кодеки: Opus, G.711, L16. Сигнализация TLS есть, SRTP нет.
* Голосовой чат группы требует, чтобы аккаунт-шлюз был в ней и мог начинать голосовой чат; без `calls.group_chat`
  `/group` создаёт конференцию Telegram. Пока разговор в групповом звонке, DTMF по этой линии из чата не отправить.
* Конференции Telegram проверены на фейковом NTgCalls и по протоколу, живого прогона с несколькими участниками ещё
  не было.
* На Windows выход из процесса идёт через `TerminateProcess`, это ограничение библиотеки ntgcalls.
